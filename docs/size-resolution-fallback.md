# 尺寸支持、分辨率分流与交付准则

## 1. 分辨率分流策略（1K 默认 / 2K 普通 / 4K 显性）

本技能采用双 Key 动态分流架构：

- **1K 模式（默认）**：使用普通 Key。支持 `1024x1024`、`1280x720`、`1536x1024`、`1024x1536`、`1824x1024`、`2048x1152` 等（完整矩阵见第 3 节）。
- **2K 模式**：仍使用普通 Key，不进 4K 付费路由。支持 `2048x2048`、`2048x1152`、`2048x1360`、`1360x2048`、`1152x2048`、`2048x1536`、`1536x2048`、`2048x896`、`896x2048`。
- **4K 模式（显性要求）**：使用 4K 专用 Key，且**自动走异步任务接口**、**强制使用 `gpt-image-2.5-flare`**。支持 `2880x2880`、`3520x2336`、`2336x3520`、`3840x2160`、`2160x3840`、`3312x2480`、`2480x3312`、`3840x1648`、`1648x3840`、`4096x4096`。

脚本会自动推断档位：最大边 ≤1536 判为 1K，1537~2048 判为 2K，>2048 判为 4K。也可以用 `--resolution 1k|2k|4k` 显式指定。

## 2. 原生分辨率与上游限制

当前扩散生图模型在底层隐空间扩散推理时，出于显存与算力约束，原生渲染分辨率与请求尺寸并不总是 1:1。**必须按接口实际返回的像素尺寸判断是否需要升级**：

| 请求尺寸 | 档位 | 实测返回参考尺寸 |
|---|---|---|
| `1024x1024` | 1K | `1254x1254` |
| `1344x1024` | 1K | `1437x1095` |
| `1824x1024` | 1K | `1672x940` |
| `2048x1152` | 2K | `1672x941` |
| `3840x2160` | 4K | `3840x2160`（4K 账户组可返回真 4K） |

> 4K 账户组实测能返回真正的 3840×2160；非 4K 路由下 2048 级请求返回的是约 1672~1792 宽的原生图，与请求尺寸有差距，交付时必须如实汇报实际尺寸。

## 4. 严禁本地二次插值

- **原则**：严禁在本地使用工具（如 sips、Pillow 等）将低分辨率图片插值拉伸为伪高分辨率。插值拉伸无法增加真实细节，反而会导致 UI 文字、表格和线条发虚模糊。
- **交付要求**：直接如实交付 API 返回的原汁原味文件，并在回复中清晰告知实际像素尺寸与所用档位。

## 5. 模型与 4K 的硬约束

- `gpt-image-2.5-sunburst` **不在 4K 账户组**，4K 请求会返回 HTTP 404；脚本在 4K 时自动切到 `flare`，显式 `--model sunburst --4k` 会直接拒绝。
- `gpt-image-2` 兼容通道在 4K 账户组实测可用（返回真 4K），可用 `--model image-2 --4k` 复现历史口径。
